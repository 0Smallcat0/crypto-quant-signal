## 0. Why this measurement, and why now

Iteration 27 recorded that "of six gates, two have ever decided a
candidate", and that gates 5 and 6 "have never been executed". Since then
the loop has measured, one at a time, **what each gate can actually
decide** rather than what it says:

|---|---|---|
| 1 Trial registry | iteration 27 | process discipline; `effective_N` is a recorded contract deviation |
| 2 Data floor | iteration 27 | **cannot bind** — all 133 trials share one 2676-day window against a 1000-day floor |

| 5 Holdout | iteration 63 | a dead strategy clears it **30.91 %** of the time; an intact one fails **30.1 %** |

Gate 6 is the last one, and it is the only gate with a **live deadline**:
`GATE6_BASELINE_2026-07-25.md` section 3.1 names **2026-10-03** as the
earliest date its first checkbox can be ticked, and iteration 58 measured

**2026-10-01** — eleven days from today.

The question asked here is the one iteration 63 asked of gate 5 and
arXiv 2609.14859 (Hall, 2026-09-14) asks of commercial evaluation gates:
**what does this gate do to a subject with nothing behind it?**

## 2. The measurement: clause by clause

Gate 6 is `docs/contracts/VALIDATION_GATE_CONTRACT.md:92-101`. It
decomposes into ten checkable clauses. For each, two separate questions
were asked — *can it fail at all?* and *is it easier to pass when the
runtime emits nothing?*

| # | Clause (line) | Measured today | Can it fail for a **deciding** runtime? | Can it fail for a runtime emitting **nothing**? |
|---|---|---|---|---|
| C1 | runs >= 3 calendar months (94) | day 80 of 93 | no — calendar time | no — calendar time |
| C2 | 0 real order attempts (95) | 0 (9 paper orders) | **no** | **no** |
| C3 | 0 private API usage (95) | 0 | **no** | **no** |
| C4 | 0 critical crashes (95) | 0; exits 0 every day | yes | **no** |
| C5 | ledger reconciliation passes (96) | **not implemented** | **no** | **no** |
| C6 | every fill has fee/slippage (96) | **9/9** | yes | **no** |
| C7 | every reject has a reason code (97) | **1/1** | yes | **no** |
| C8 | no duplicate notifications/orders across restarts (97) | 0 duplicates | **no** | **no** |
| C9 | measure actual costs (98-99) | **frozen 2026-07-30** | obligation, no bar | **cannot fulfil** |
| C10 | round-trip > ~45 bps -> recalibrate (100-101) | 20.00 / 20.10 bps, frozen | yes | **no** |

Each "no" in the fourth column is a structural fact with a file and a
line behind it, not a judgement:

- **C2 — there is no real-order code path.** The only broker in the
  repository is `PaperBroker` (`src/execution/broker.py:34`); the only
  HTTP POSTs in `src/` are Discord notifications
  (`src/notify/channels.py:87,130`). A clause counting real order attempts
  cannot fail in a codebase that cannot place one.
- **C3 — private API usage is rejected at config-load time.**
  `src/config/models.py:129-133` routes `private_api_enabled` and
  `api_key_required` into `_reject_enabled_flag`, which **raises**
  `ValueError` if either is true (`src/config/models.py:30-34`). The
  process does not start if the clause would be violated.
- **C5 — "ledger reconciliation" has no implementation, by design.**
  `grep -rni reconcil` over the whole tree returns **two** hits outside
  `.venv/`, both in `tests/backtest/test_engine_parity.py` — one a
  docstring line (`"were reconciled by hand to bit-identical Decimal
  equity once (2026-07-03)"`) and one a test-function name
  (`test_backtest_and_runtime_replay_reconcile_on_shared_history`). Both
  are about **backtest-vs-runtime engine parity**, not about reconciling a
  ledger against broker state, which is what C5 asks for. And the absence
  is deliberate:
  `docs/ENGINEERING_DECISIONS.md:41` records the 2026-07-03 decision to
  accept "redundant state in the log ... in exchange for a two-level
  recovery lattice **with no reconciliation pass**." Gate 6 requires a
  check the architecture was explicitly designed not to have — decided the
  same day the paper period began.
- **C8 — duplicates are refused by the data structure.**
  `src/runtime/store.py:111-112`: `if key in self._keys: return False`.
  The store's own module docstring states it verbatim: "duplicate keys are
  refused, which is what makes a restart unable to re-send or re-execute
  anything." No three-month observation is involved; the clause is a
  property of the append path.

C2, C3, C5 and C8 are therefore **vacuous**: they would read "pass" on the
first day, with the runtime never started. C4, C6, C7 and C10 are
falsifiable — but only by activity, so the dead runtime is the safest
possible subject. C1 is activity-independent.

## 3. The direction of the monotonicity, stated exactly

C6 and C7 are of the form "every X has Y". Their failure probability is
`1 - (1-p)^n` in the number of events `n`. Measured rates over the 28
decision days: **0.3214 fills/day** and **0.0357 rejections/day**. Over
the 93-day window a deciding runtime would produce about **29.9 fills**
and about **3.3 rejections**; the actual window will contain **9** and
**1**. So the dead runtime is graded on **30.1 %** of the exposure —
roughly **20.89 fills** and **2.32 rejections** of failure opportunity
forgone.

C4 is stronger than "less likely": the early return at
`engine.py:202` means the downstream code **cannot** crash, because it is
not reached. `CryptoQuantDailySignalCycle` reports `LastTaskResult=0`
every day (iteration 57), and 51 consecutive health rows confirm it.

C10 is the sharpest case. The recalibration trigger needs round-trip
> 45 bps against `2 x median_spread + 2 x 10 bps` fees, i.e. a per-side
spread above **12.5 bps**. Recomputed on the full frozen sample:

| Symbol | Quotes | Quote days | Window | Median spread (bps) | Max (bps) | Round-trip (bps) |
|---|---:|---:|---|---:|---:|---:|
| BTCUSDT | 28 | 28 | 2026-07-03 -> 2026-07-30 | 0.0000 | 0.0000 | **20.00** |
| ETHUSDT | 28 | 28 | 2026-07-03 -> 2026-07-30 | 0.0500 | 0.0600 | **20.10** |

The ETH spread would have to be **250x** its median (**208x** its observed
maximum) to fire C10; on BTC the observed spread is identically zero, so
no multiple reaches it. And the sample **cannot grow** — zero `exec_quote`
events have been emitted in 51 days. C10 is not merely unfired; it is
frozen below its trigger permanently.

## 4. The one clause a dead runtime fails carries no verdict

**C9 is the exception, and it is the whole point.** "Measure actual
costs: current exchange fee schedule, observed spread, and
notification->execution delay" is the only clause whose subject is the
*presence* of evidence rather than the *absence* of faults. A runtime
emitting nothing cannot satisfy it — and gate 6 attaches **no pass/fail
bar to it**. The bar in the neighbourhood (C10) tests the measured value,
not whether a measurement exists.

So of ten clauses: **nine carry a verdict and not one of them can be
failed by a runtime that emits nothing**, and the single clause that a
dead runtime demonstrably cannot satisfy is the one clause with no verdict
attached. **Gate 6's pass probability for a subject that never decides
anything is 1.0, by construction.** It is not a near-coin-flip like gate 5
(30.91 % / 30.1 %, iteration 63); it is a certainty.

Restated from the other side, and this is the fair framing: C2, C3 and C8
being unfailable is **good engineering** — product law and idempotency are
enforced in types, config validators and the append path rather than by
operator discipline. The defect is not that these invariants hold. It is
that **gate 6 credits them as three months of accumulated paper-trading
evidence** when they are load-time and write-time properties that would
read "pass" with the process never started.

One check in the repository does distinguish the dead window from a live
one: `GATE6_BASELINE_2026-07-25.md` **section 3.1 checkbox 2** — "Gate-6
baseline table refreshed with **>= 60 quote days**; round-trip cost still
<= 45 bps."

- Observed: **28** quote days, **46.67 %** of the bar, frozen for **52**
  days.
- Had the runtime stayed alive, the 60th quote day would have arrived on
  **2026-08-31** — twenty days ago.
- Section 2's own re-check trigger ("re-check at N >= 60 quotes", written
  2026-07-25 at N=44) stands at **N=56** and can never reach 60. Iteration
  57 stated this correctly — "the reason the threshold had not been
  crossed turned out to be the finding" — and that wording is confirmed
  here, not corrected.

**That checkbox lives in a research document, not in a contract.** It is
not frozen, not append-only, and any iteration may edit it. The single
instrument in this program capable of failing a dead paper period has none
of the protections the gates have, and the gate that is protected cannot
fail it.

## 6. What this does and does not establish

**Establishes.** (i) Gate 6 as written is monotone in the wrong direction:
nine verdict-carrying clauses, none failable by an inactive runtime, four
of them unfailable by any runtime. (ii) Its one activity-sensitive
requirement, C9, has no bar. (iii) The specific window it will be applied
to contains **28 deciding days out of 93** (**30.11 %**) and **9 of about
30** fills. (iv) `ledger reconciliation` is unimplemented and was
deliberately designed away on 2026-07-03. (v) The cost-recalibration
trigger sits **250x** above the frozen sample's median spread and the
sample cannot grow. (vi) The only bar that would catch this is an unfrozen
checkbox in a research file.

**Does not establish.** (i) That the runtime is unsound — iteration 57
identified a specific off-by-one, and the invariants in C2/C3/C8 are
genuinely enforced. (ii) That gate 6 would be passed **dishonestly** — no
one has ticked anything, and the dashboard discrepancy is iteration 58's
finding, not a new allegation. (iii) That a *repaired* gate 6 would fail
this strategy — that is unknown and unmeasurable until the runtime decides
again. (iv) Anything whatsoever about whether the **edge** works. Gate 6
is a process gate; like the three October tests (iteration 62) and the
October holdout (iteration 63), it cannot speak to return.

**Route closed:** no document, report or proposal may treat a gate-6 pass
— in October 2026 or later — as evidence that the paper period validated
the runtime, unless the window it covers is reported alongside it with its
deciding-day count. A gate whose null subject passes with probability 1
certifies nothing about the subject that passes it.

**With this, all six gates are characterised.** Gate 2 cannot bind, gate 6
cannot fail, gates 3 and 4 decide and both carry recorded defects, gate 5
is a near-coin-flip, and gate 1 is process discipline. **No document may
say this program "survived six gates"** — iteration 27's rule, now resting
on six measurements rather than four.

## 7. Three options for the operator

This is the **seventh** operator choice now due, and the second with a
hard October date attached.

**(A) Tick nothing, and record why.** On 2026-10-01 the dashboard's
observation bar reaches 100 % and on 2026-10-03 section 3.1's first
checkbox becomes date-eligible. Leave both unticked and record that the
gate-6 window contained 28 deciding days of 93. Costs nothing; the benefit
is that the program does not acquire a sixth "pass" that means nothing.
**This is the option the loop would take if it were permitted to decide.**

**(B) Repair the runtime first, restart the gate-6 clock, and re-date the
window.** The off-by-one is one constant (`_LIVE_FETCH_LIMIT = 400`,
`scripts/run_paper_runtime.py:59`, iteration 57). Fixing it is an operator
act — iron rule 1 forbids the loop from touching it. A clock restarted on
the repair date reaches three months no earlier than **2027-01**, and that
is the honest earliest date for any gate-6 verdict about the current
strategy.

**(C) Amend gate 6 to require decisions, not days, before it is next
applied.** The minimum repair is a quorum clause — e.g. ">= N deciding
cycles and >= M fills inside the window" — plus giving C9 a bar ("a cost
measurement must exist for >= X quote days"). **This is a rule change and
must be declared before the window it governs**, exactly as iteration 27
required for `effective_N` and iteration 64 for the anti-dilution rule.
Amending it after 2026-10-03 while looking at a window it would have
failed is the change-the-rules-after-seeing-results failure the gate
contract's own anti-rules forbid.

Nothing here is a recommendation the loop may act on. All three options
require the operator, and (C) has a deadline of **2026-10-03**.
